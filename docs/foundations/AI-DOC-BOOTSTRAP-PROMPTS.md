# VibeCoding 文档系统 AI 提示词包

Last Updated: 2026-03-11
Status: Active

## 1. 目标

这份文档给普通开发者一组可以直接复用的提示词，用于让 AI 帮助创建、迁移、维护文档系统。

原则：

- 提示词只要求 AI 做它擅长的事
- SSOT 和边界仍由人确认
- 每个提示词都要求 AI 输出明确文件与动作
- 文档状态应按 `Draft -> Active -> Snapshot -> Archive` 生命周期处理

## 1.1 状态处理规则

让 AI 参与文档工作时，建议在提示词里默认携带以下约束：

- 新生成文档默认标为 `Draft`
- 只有 metadata 和核心内容都补齐后，才允许切换到 `Active`
- 若旧文档被新的 SSOT 替代，应建议标记为 `Snapshot`
- 若文档只保留历史留痕，不再进入当前入口，应建议标记为 `Archive`

这样可以减少 AI 在没有足够上下文时，把半成品文档误标成 `Active`。

## 2. 使用方法

每次使用提示词前，先补 4 项上下文：

- 项目目标
- 当前阶段
- 已有文档清单
- 当前最混乱的问题

如果项目已有代码或产品状态，再加：

- 当前真实实现状态
- 最近一次主要改动

## 3. 提示词 A：从零启动文档系统

适用场景：

- 新项目
- 还没有文档体系
- 想快速建立最小起步包

可直接复用：

```text
请基于下面的项目信息，为我设计一套最小可运行的 VibeCoding 文档系统。

项目目标：<填写>
当前阶段：<填写>
核心主流程：<填写>
当前最担心的混乱：<填写>

请完成以下事情：
1. 给出推荐的 docs 目录结构，但只保留最小必需文档
2. 明确每份文档的角色、SSOT 边界、更新触发器
3. 直接生成最小 8 份文档的草稿目录和标题，并将新文档默认标为 `Draft`
4. 告诉我哪些内容必须由我人工确认
5. 不要生成过度复杂的企业级体系
```

## 4. 提示词 B：改造一个已有但混乱的项目

适用场景：

- 已有很多文档
- 目录混乱
- 状态、需求、规则分散

可直接复用：

```text
请把下面这个已有项目的文档体系做一次角色梳理和迁移建议。

项目背景：<填写>
当前真实状态：<填写>
已有文档列表：<填写>
当前最明显的冲突：<填写>

请输出：
1. 现有文档按 governance/strategy/product/design/engineering/delivery/operations 的归类结果
2. 哪些文档应作为 SSOT，哪些应标记为 Snapshot
3. 哪些文档只是命名不当，哪些文档内容角色本身就错了
4. 哪些文档应保持 `Draft`，哪些可以升级成 `Active`
5. 最低成本的迁移顺序
6. 不要直接大搬家，优先做口径收敛
```

## 5. 提示词 C：为新功能创建功能包

适用场景：

- 新功能跨多个页面或模块
- 想一次性补齐产品、设计、Spec、验收

可直接复用：

```text
请为这个功能创建一个可执行的 feature package 文档方案。

功能名称：<填写>
用户问题：<填写>
核心流程：<填写>
涉及页面/模块：<填写>
当前约束：<填写>

请输出：
1. features/<feature>/ 下应包含的文档清单
2. 每份文档的作用和边界
3. 每份文档的推荐初始状态，并说明何时从 `Draft` 升级到 `Active`
4. PRD、WIREFLOW、TECH-SPEC、ACCEPTANCE、ANALYTICS 的最小章节草案
5. 哪些内容需要先从全局原则和术语表继承，避免重复定义
```

## 6. 提示词 D：让 AI 协助每轮迭代更新文档

适用场景：

- 每轮功能变更后需要同步文档
- 想降低漏更成本

可直接复用：

```text
请根据下面这轮迭代的实际改动，给出需要更新的文档清单，并直接起草改动。

本轮改动：<填写>
受影响模块：<填写>
受影响页面：<填写>
是否改了业务规则：<是/否>
是否改了字段/状态机/事件：<是/否>

请输出：
1. 必须更新的文档列表
2. 每份文档为什么需要更新
3. 建议修改的段落或章节
4. 哪些文档状态应保持不变，哪些应从 `Draft` 切到 `Active`
5. 哪些旧文档需要标记为 `Snapshot`
6. 不要重复修改不相关文档
```

## 7. 提示词 E：做发布前文档对账

适用场景：

- 准备发布
- 想确认文档与实现一致

可直接复用：

```text
请基于下面的版本改动，做一次发布前的文档对账检查。

版本范围：<填写>
主要功能改动：<填写>
主要风险点：<填写>
当前文档入口：<填写>

请检查并输出：
1. 哪些 SSOT 文档必须更新后才能发布
2. 验收清单是否覆盖了这次改动
3. Analytics/Runbook/Release Notes 是否缺失
4. 是否还有应为 `Draft` 却被错误标成 `Active` 的文档
5. 是否还有旧状态、旧文案、旧规则残留在文档中
6. 给出最小修正文档动作
```

## 8. 提示词 F：做术语和口径巡检

适用场景：

- 长期迭代后术语开始漂移
- 团队对同一概念叫法不一致

可直接复用：

```text
请对下面项目的文档做一次术语和口径一致性检查。

核心术语：<填写>
文档目录范围：<填写>
已知易混概念：<填写>

请输出：
1. 存在冲突或歧义的术语列表
2. 每个术语当前在哪些文档里表达不一致
3. 建议统一到 glossary 的标准表述
4. 哪些文档需要回写修正
5. 哪些只是历史快照，不应纳入当前口径
```

## 9. 使用注意事项

不要让 AI 直接决定：

- 业务规则最终版本
- 是否删除历史文档
- 哪个旧方案彻底废弃
- 技术命名的长期兼容策略

应该让 AI 先做：

- 结构整理
- 冲突检查
- 草案生成
- 导航和互链更新

## 10. 结论

对普通开发者，最有效的方式不是学习一整套理论，而是：

1. 先理解文档角色
2. 再使用固定提示词
3. 用模板起步
4. 把更新嵌进迭代节奏

这样 AI 才会成为“文档系统的加速器”，而不是新的噪音来源。
