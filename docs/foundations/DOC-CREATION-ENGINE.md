# VibeCoding 文档创建引擎

Last Updated: 2026-03-11
Status: Active

## 1. 目标

这份文档研究的不是“文档应该有哪些类型”，而是如何把这些文档真正创建出来，并持续活下去。

核心问题：

- 新项目如何从 0 启动文档系统
- 已有混乱项目如何迁移到这套系统
- AI 在创建中应该做什么，不应该做什么
- 如何把文档更新变成日常机制，而不是阶段性整理

## 2. 核心模型

文档系统要真正落地，必须有一套创建引擎。

这个引擎由五个动作组成：

1. `inventory`：盘点已有事实和文档
2. `classify`：给现有内容归位
3. `bootstrap`：补齐最小起步集
4. `operate`：把文档更新嵌入迭代
5. `archive`：给过时内容降级或归档

如果缺任意一个动作，系统都会很快失效。

## 3. 启动路径

### 3.1 路径 A：从零开始的新项目

建议顺序：

1. 建立 `governance` 起步包
2. 建立 `strategy` 起步包
3. 为第一条主流程建立 `feature package`
4. 为第一条主流程建立 `acceptance`
5. 当项目进入第二轮以上迭代，再补 `delivery` 和 `operations`

最小顺序如下：

1. `PROJECT-CONSTITUTION`
2. `DOCUMENT-MAP`
3. `GLOSSARY`
4. `PRODUCT-PRINCIPLES`
5. `ROADMAP-STATUS`
6. `FEATURE-PRD`
7. `TECH-SPEC`
8. `ACCEPTANCE-CHECKLIST`

### 3.2 路径 B：已有项目的迁移改造

建议顺序：

1. 盘点已有文档和真实代码状态
2. 识别 `状态 SSOT`、`需求 SSOT`、`设计 SSOT`、`Spec SSOT`
3. 先修正文档角色，再考虑迁目录
4. 给历史稿打 `Snapshot`
5. 清掉重复维护的状态和旧命名
6. 再开始补缺失文档

迁移时最忌讳直接“大搬家”。

先收口角色，再迁文件，成本最低。

## 4. 创建引擎的输入

AI 或开发者要创建文档，先收集 6 类输入：

1. 项目目标
2. 当前阶段
3. 核心主流程
4. 已有文档清单
5. 当前最大混乱点
6. 当前真实代码或产品状态

如果这 6 项都没有，AI 就只能生成漂亮但不可靠的文件结构。

## 5. 创建引擎的输出

一轮有效的文档创建，输出不应只是“多几个 md 文件”。

至少应输出：

1. 文档目录建议
2. SSOT 分配表
3. 缺失文档清单
4. 最小模板落地文件
5. 导航与互链更新
6. 历史文档处理动作

## 6. AI 与人的职责分工

### 6.1 AI 适合负责

- 起草目录结构
- 给现有文档归类
- 把已有结论迁入模板
- 检查术语和状态冲突
- 生成导航和互链
- 生成定期更新 checklist

### 6.2 人必须负责

- 决定谁是 SSOT
- 决定产品边界
- 决定技术命名和长期兼容策略
- 决定哪些旧文档保留为 `Snapshot`
- 确认发布和运营口径

原则很简单：

- AI 擅长组织和补齐
- 人必须负责最终裁决

### 6.3 状态切换规则

AI 和人协作创建文档时，应默认遵守同一条状态流程：

1. 新生成文档默认标为 `Draft`
2. 补齐 metadata 和核心内容后，再切到 `Active`
3. 被更新版本替代的旧文档，降级为 `Snapshot`
4. 只保留留痕、不再进入当前入口的文档，降级为 `Archive`

不要跳过中间阶段，直接把刚生成的半成品文档视为 `Active`。

## 7. 将文档创建嵌入日常开发

一套系统要活下去，必须变成固定节奏，而不是额外工作。

### 7.1 功能启动时

至少执行：

1. 建或更新 `feature PRD`
2. 建或更新 `feature TECH-SPEC`
3. 建或更新 `feature ACCEPTANCE`
4. 新建文档默认先保持 `Draft`

### 7.2 开发中变更时

按变化类型更新：

- 范围变化：更新 PRD
- 状态机/字段变化：更新 Spec
- 页面主流程变化：更新 Wireflow 或 Acceptance
- 事件变化：更新 Analytics
- 如果某份文档已经补齐并将被依赖，再切换到 `Active`

### 7.3 每轮迭代结束时

至少执行：

1. 更新 `ROADMAP-STATUS`
2. 更新本轮受影响的验收清单
3. 给过时分析稿打 `Snapshot`
4. 若上线，补 `RELEASE-NOTES`
5. 检查是否还有应为 `Draft` 却被错误标成 `Active` 的文档

### 7.4 故障或争议出现时

出现以下情况，必须触发文档动作：

- 团队对产品行为理解不一致
- AI 连续多次改错同一类问题
- 页面行为与文案冲突
- 测试结果与预期口径冲突
- 发布后出现线上事故

## 8. 文档创建的三种机制

### 8.1 手动机制

适合：

- 单人项目
- 文档量少
- 初期阶段

方法：

- 按模板手工创建
- 每轮迭代结束后人工更新

### 8.2 AI 协助机制

适合：

- 已有基础文档
- 开始多轮迭代
- 需要提高同步效率

方法：

- 人给最小上下文
- AI 起草变更和新文档
- 人确认 SSOT 和边界
- AI 回写导航与互链

### 8.3 仪式化机制

适合：

- 小团队协作
- 已上线项目
- 文档必须持续稳定

方法：

把文档更新挂到固定节点：

- `feature kickoff`
- `before merge`
- `before release`
- `after release`
- `postmortem`

## 9. 文档创建的门禁规则

建议建立简单门禁，而不是复杂流程。

### 9.1 Feature Kickoff Gate

进入开发前，至少确认：

- 范围有 PRD
- 行为有 Spec
- 验收有 Checklist

### 9.2 Merge Gate

合并前，至少确认：

- 本次改动涉及的 SSOT 已更新
- 回归清单能覆盖主流程
- 文案和 UI 没与产品原则冲突

### 9.3 Release Gate

发布前，至少确认：

- Release Notes 已生成
- 关键事件可观测
- Runbook 可处理失败场景

## 10. 普通开发者可直接执行的落地法

如果只想快速启用这套系统，按下面做：

1. 用模板创建最小 8 文档
2. 用 `DOCUMENT-MAP` 指定 SSOT
3. 任何新功能都按 feature package 新建文档
4. 每轮迭代只更新 4 类文档：状态、PRD、Spec、Acceptance
5. 任何历史稿不删除，改标 `Snapshot`

这样做的好处是：

- 成本低
- 可持续
- AI 有稳定入口
- 未来要扩完整系统时不必重来

## 11. 研究结论

如何推动文档创建，核心不是要求开发者“更自觉”，而是建立一套低摩擦机制：

1. 有固定的起步顺序
2. 有清晰的触发器
3. 有模板
4. 有 AI 提示词
5. 有固定更新节点
6. 有归档规则

只有这样，这套文档系统才会真正成为 VibeCoding 的基础设施，而不是一轮整理后的静态文件夹。
