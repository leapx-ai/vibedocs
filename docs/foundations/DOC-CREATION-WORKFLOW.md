# VibeCoding 文档创建与维护机制

Last Updated: 2026-03-11
Status: Active

## 1. 目标

这份文档回答的不是“文档长什么样”，而是：

- 什么时候该创建哪份文档
- 谁来创建
- 如何让 AI 参与创建而不制造噪音
- 文档如何持续维护，而不是写完就死

## 2. 创建原则

1. 先有角色，再有模板
2. 先有 SSOT，再允许扩展
3. 先解决当前阶段的问题，不一次性铺满全部文档
4. 文档必须有更新触发条件，否则就是死文档
5. AI 可以起草文档，但人必须确认 SSOT 和边界

## 3. 四阶段创建法

### 阶段 A：项目启动

目标：让团队和 AI 至少知道“边界、术语、状态入口”。

必须创建：

1. `PROJECT-CONSTITUTION.md`
2. `DOCUMENT-MAP.md`
3. `GLOSSARY.md`
4. `ROADMAP-STATUS.md`

通过标准：

- 团队知道哪个文档维护状态
- 同一术语不会在不同文档里有不同含义
- AI 知道该先看哪些文档

### 阶段 B：第一条主流程落地

目标：让“做什么、怎么做、怎么验收”三件事闭环。

必须创建：

1. `PRODUCT-PRINCIPLES.md`
2. `FEATURE-PRD.md`
3. `TECH-SPEC.md`
4. `ACCEPTANCE-CHECKLIST.md`

通过标准：

- 功能范围清楚
- 技术实现边界清楚
- 验收步骤可执行

### 阶段 C：进入多迭代开发

目标：让节奏、任务、回归可持续。

建议创建：

1. `TASK-LIBRARY.md`
2. `REGRESSION-CHECKLIST.md`
3. `TESTING-REPORT.md`

通过标准：

- 当前进度只在一个地方维护
- 任务拆分不重写需求
- 测试和回归有独立执行入口

### 阶段 D：进入上线与运营

目标：让上线、配置、运营、复盘不依赖口口相传。

建议创建：

1. `ANALYTICS-EVENTS.md`
2. `RUNBOOK.md`
3. `RELEASE-NOTES.md`
4. `POSTMORTEM.md`

通过标准：

- 发布可追溯
- 线上异常有处理入口
- 数据事件有统一口径

## 4. 文档创建触发器

普通开发者不需要思考“要不要写文档”，只要看触发器。

### 4.1 创建 Governance 文档的触发器

- 新项目启动
- 团队开始多人协作
- AI 开始频繁参与实现

### 4.2 创建 Product / Feature 文档的触发器

- 新功能跨越多个页面或模块
- 出现“这个功能到底算什么”的讨论
- 需求反复改，说明边界不清

### 4.3 创建 Spec 文档的触发器

- 出现稳定字段、接口、状态机
- 多人协作实现同一功能
- 同一逻辑需要被多端或多模块复用

### 4.4 创建 Delivery 文档的触发器

- 工作项超过 5 个
- 一轮迭代超过 1 周
- 开始出现“谁在做什么”不清晰

### 4.5 创建 Operations 文档的触发器

- 准备上线
- 开始接入付费、埋点、远程配置
- 出现需要排障、回滚、对账的场景

## 5. AI 驱动创建法

AI 最适合做三类工作：

1. 结构起草
2. 内容归类
3. 口径对齐

AI 不适合单独决定：

1. 哪个文档是 SSOT
2. 产品边界最终取舍
3. 关键命名是否进入正式规范

### 5.1 推荐工作流

1. 人先给出最小上下文：
   - 项目目标
   - 当前阶段
   - 已有文档
   - 当前最痛的混乱点
2. AI 输出：
   - 推荐文档结构
   - 缺失文档清单
   - 最小模板草案
3. 人确认：
   - 哪些文档成为 SSOT
   - 哪些只是参考稿
4. AI 再执行：
   - 创建文件
   - 更新导航
   - 清理互相冲突的旧引用

## 6. 每次迭代的维护动作

每次迭代结束后，只做 5 件事：

1. 更新 `ROADMAP-STATUS`
2. 更新本轮改动触发的验收清单
3. 若范围变化，更新 PRD
4. 若字段/事件变化，更新 Spec
5. 若结论已过时，给旧文档打 `Snapshot`

这 5 步比“整理所有文档”有效得多。

## 7. 文档负责制

哪怕是单人项目，也建议给文档分配“角色负责人”。

| 文档族 | 默认负责人 |
|---|---|
| Governance | Tech Lead / 项目 owner |
| Strategy | Product owner |
| Product | PM / 功能 owner |
| Design | Designer / 前端 owner |
| Engineering | Tech Lead / 实现 owner |
| Delivery | 项目 owner / 执行 owner |
| Operations | 发布 owner / 运营 owner |

单人项目里，这些角色可以是同一个人，但角色意识不能省掉。

## 8. 文档健康度检查

每 1-2 周做一次快速检查：

### 8.1 结构检查

- 有没有一个问题对应多个 SSOT
- 有没有重要问题没有文档承接
- 有没有明显放错目录的文档

### 8.2 内容检查

- 是否还在引用已经失真的数字或状态
- 是否存在多个术语指向同一概念
- 是否有历史快照冒充当前状态

### 8.3 执行检查

- AI 是否知道先读什么
- 新人是否知道文档入口
- 验收是否可直接照文档执行

## 9. 最终目标

这套系统的最终目标不是“文档更漂亮”，而是：

- 让 AI 产出更少返工
- 让普通开发者也能维持高质量文档
- 让项目在需求、实现、验收、上线、复盘之间形成闭环

如果一套文档系统不能提升这三件事，它就只是更复杂的文件夹。
