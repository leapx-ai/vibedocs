# 为什么产品需要面向 Agent 设计

Last Updated: 2026-03-25
Status: Active

## 1. 目标

这份文档讨论一个正在变得越来越重要的判断：

**未来很多 IT 产品，不会只对人类开放，也会对 agent 开放。**

这里关注的不是某个具体模型，也不是某一类自动化工具，而是一个更底层的趋势：

- 软件不再只需要“被人使用”
- 软件还需要“被 agent 稳定理解、调用、协作和持续操作”

这会改变产品设计、文档设计和系统边界设计。

## 2. 从 GUI 到 CLI，再到 Agent

软件产品的发展，通常会经历几个典型阶段：

1. 先让系统能工作
2. 再让人更方便地操作它
3. 然后让程序也能稳定调用它

过去最明显的变化是：

- 从只有内部接口，到有 GUI
- 从只能点按钮，到有 CLI 和 API

而现在正在发生的新变化是：

- 从“软件主要给人用”
- 逐步走向“软件也要给 agent 用”

这不是 GUI 会消失，而是产品要开始接受一个事实：

**人类用户不再是唯一用户。**

## 3. 为什么 agent 会成为更大的市场

如果只看单体价值，人类用户仍然很重要。

但如果看规模和调用频率，agent 的潜在数量会远超人类：

- 一个团队只有几十个人，但可能同时运行数百个 agent 流程
- 一个公司的人数有限，但 agent 可以覆盖研发、测试、运营、巡检、发布、支持等大量重复工作
- 人一天只能完成有限轮操作，但 agent 可以持续执行、持续检查、持续回写

也就是说，agent 不是“附加插件”，而会逐步变成一类主要用户。

这会带来一个很现实的变化：

**产品不能只考虑“人是否能看懂”，还要考虑“agent 是否能稳定工作”。**

## 4. 这会改变什么

一旦把 agent 视为主要用户之一，产品设计重点就会变化。

过去常见的思路是：

- 页面是否顺手
- 操作路径是否短
- 信息是否易于人理解

而面向 agent 时，还必须补上这些问题：

- 系统是否可加载
- 状态是否可判定
- 入口是否可发现
- 权威来源是否可区分
- 变更是否可路由
- 错误是否可反馈

所以，很多过去被当作“辅助层”的东西，会慢慢变成产品能力本身：

- 文档
- 状态
- 规则
- 结构化输出
- 操作协议

## 5. 为什么文档和规则会变成产品能力

当产品只面向人时，很多信息可以通过：

- 口头同步
- 页面说明
- 团队默契
- 临时聊天记录

来补足。

但对 agent 来说，这些方式都不稳定。

agent 真正能依赖的，是：

- 稳定入口
- 明确结构
- 唯一事实来源
- 清晰状态
- 可执行规则

也就是说，文档和规则不再只是“辅助材料”，而是系统可操作性的基础设施。

从这个角度看，未来产品竞争力的一部分会变成：

**它是不是容易被 agent 正确使用。**

## 6. 什么叫“面向 Agent 的产品能力”

面向 agent，不等于简单地加一个 API。

真正面向 agent 的产品，至少要具备这些能力：

1. **可进入**
   agent 知道从哪里开始理解系统。

2. **可判定**
   agent 能判断当前状态、边界和成熟度。

3. **可路由**
   agent 知道一类变化应该落到哪里。

4. **可约束**
   agent 知道哪些事不能直接决定，哪些冲突必须上交。

5. **可反馈**
   agent 能在执行后得到漂移、缺失、冲突等反馈。

如果缺少这些能力，agent 看起来能做很多事，但很难稳定地持续工作。

## 7. 为什么这对项目型产品尤其重要

在项目型软件里，agent 的价值更大。

因为项目型工作天然包含很多连续动作：

- 理解背景
- 拆任务
- 起草文档
- 更新实现
- 做验证
- 回写状态
- 生成发布信息

如果每一步都要靠人重新解释上下文，agent 的效率优势就会被抵消。

所以项目型产品如果想真正用好 agent，就必须建立一套让 agent 能持续进入和持续工作的系统。

也就是说，面向 agent 的能力不是“锦上添花”，而是未来的基础层。

## 8. 为什么这类产品要从“人机共用”而不是“只给 agent 用”开始

虽然 agent 可能成为更大的市场，但这不意味着系统要只服务 agent。

更现实的方向是：

**让同一套系统同时服务人和 agent。**

原因很简单：

- 人仍然负责目标、边界和最终裁决
- agent 负责推进、生成、检查和回写
- 如果两者使用的不是同一套事实系统，漂移只会更快

所以最稳的设计不是做两套平行系统，而是：

- 人能看懂
- agent 能操作
- 双方共享同一套入口、状态和规则

## 9. 这为什么会成为一个独立市场

因为一旦 agent 成为主要用户之一，就会出现新的需求层：

- 不是“有没有 GUI”
- 而是“能不能被 agent 稳定操作”

这会催生一整类新的产品能力：

- agent-friendly docs
- agent operating protocol
- audit and feedback loops
- state-aware task routing
- structured release and change surfaces

也就是说，未来会有一批产品，不再只是“给人更好的体验”，而是：

**给 agent 更可靠的工作环境。**

而这类环境，不会靠单个 prompt 自然长出来，它需要被设计、被维护、被工具化。

## 10. 对我们的启发

如果接受“agent 会成为主要用户之一”这个判断，那产品设计就要前移：

- 不是等 agent 用不好再补文档
- 而是从一开始就考虑 agent 如何进入系统

对我们来说，真正值得建设的，不只是“帮助人写文档”的工具，而是：

**帮助项目变得 agent-operable 的基础设施。**

这意味着：

- `guides` 不只是说明文件，而是 agent 的工作协议
- `scaffold/docs` 不只是模板，而是 agent 的工作地面
- `audit` 不只是检查工具，而是 agent 的反馈闭环
- `DOCUMENT-MAP`、`GLOSSARY`、状态模型，不只是治理要求，而是 agent 可操作性的基础条件

## 11. 一句话结论

未来越来越多的产品，不会只面向人类操作，而会同时面向 agent 持续工作。

因此，产品是否可被 agent 进入、理解、约束、反馈和持续使用，会逐步成为和 GUI、CLI 一样基础的能力层。
