# 付费层实施计划

Last Updated: 2026-03-12
Status: Active

## 1. 目标

把付费层从“能力设想”推进到“有明确依赖顺序、可交付里程碑和可售卖边界”的工作流产品。

付费层的完成标准不是列出更多功能，而是让团队在真实协作中获得持续价值：

- merge 前有约束
- 迭代中有持续巡检
- 周期性有健康趋势
- 团队可以定义自己的门禁
- 老项目可以低成本接入

## 2. 计划边界

本计划覆盖：

- PR 检查
- 自动巡检
- 文档健康度面板
- 团队规则包
- 迁移助手
- 行业模板包

本计划不覆盖：

- 开源模板与 scaffold
- 基础 CLI
- 共享规则引擎本身的基础语义

这些属于免费层或共享基础设施层。

## 3. 前置依赖

付费层启动前，应至少具备下面基础：

1. 免费层 CLI 可运行
2. 共享规则引擎的核心结果格式已稳定
3. `audit` 已能输出结构化结果
4. 规则严重级别与建议动作模型已固定

如果这些前置条件不成立，付费层就会变成不稳定的二次实现。

## 4. 成功标准

付费层第一轮完成后，至少应满足：

1. 团队可在 PR 中收到明确的文档更新约束
2. 系统可自动生成周期性巡检结果
3. 面板能展示基于历史快照的健康趋势
4. 团队可配置一组超出开源默认规则的门禁
5. 旧项目可以获得一份可执行的迁移建议

## 5. 执行顺序

付费层按 7 个阶段推进：

1. `Paid Foundation`
2. `PR Checks`
3. `Scheduled Audits`
4. `Health Dashboard`
5. `Team Rule Packs`
6. `Migration Assistant`
7. `Vertical Packs`

这个顺序不建议打乱。

原因：

- 没有共享基础设施，就没有一致的付费结果
- PR 检查是最强刚需，也是最容易证明付费价值的入口
- 自动巡检先生成历史快照，面板才能有数据可看
- 团队规则包会放大 PR 检查和巡检的价值
- 迁移助手和行业模板包更接近高客单扩展层

## 6. 阶段计划

### 6.1 Phase 0 · Paid Foundation

目标：

- 建立付费层的最小托管基础与结果消费链路

本阶段交付物：

- 规则结果存储模型
- 仓库身份与运行上下文模型
- PR / schedule / manual run 的执行入口定义
- 结果持久化与快照约定

阶段门禁：

- 规则结果可被持久化
- 不同运行来源使用同一结果结构
- hosted 层不修改规则语义，只消费结果

### 6.2 Phase 1 · PR Checks

目标：

- 在最关键的 merge 前节点提供文档约束

本阶段交付物：

- PR diff 消费层
- 评论输出器
- 阻断阈值配置
- “建议更新哪些文档”的映射逻辑

阶段门禁：

- 能对 PR 变更进行文档风险评论
- 能根据严重级别决定 warn 或 block
- 输出内容与 CLI audit 保持同一规则语言

商业化门槛：

- 这是第一批可独立售卖的核心能力

### 6.3 Phase 2 · Scheduled Audits

目标：

- 把巡检从“手动运行”变成“持续托管”

本阶段交付物：

- 定时执行器
- 巡检任务配置
- 周报或告警输出
- 快照留存机制

阶段门禁：

- 仓库可按固定节奏自动巡检
- 巡检结果可沉淀成历史快照
- 同一问题可在多次巡检间稳定追踪

商业化门槛：

- 形成比 CLI 明显更强的持续服务价值

### 6.4 Phase 3 · Health Dashboard

目标：

- 让团队看到趋势，而不只是单次结果

本阶段交付物：

- 仓库健康度视图
- 风险趋势图
- 未解决问题列表
- 长期未更新文档清单

阶段门禁：

- 面板数据来自真实快照，不是即时拼接
- 能区分当前问题和历史趋势
- 能按仓库 / 时间查看结果

商业化门槛：

- 面板必须回答“情况是在变好还是变坏”

### 6.5 Phase 4 · Team Rule Packs

目标：

- 让团队把自己的治理规则接进产品

本阶段交付物：

- 团队规则包模型
- 规则启用与禁用机制
- 团队级严重级别覆盖
- PR 检查与巡检联动

阶段门禁：

- 团队能覆盖默认阈值，但不能破坏核心结果结构
- 团队规则可复用，不是一次性手写脚本
- 规则包能同时作用于 PR 检查和巡检

商业化门槛：

- 形成团队级锁定价值，而不只是单仓脚本增强

### 6.6 Phase 5 · Migration Assistant

目标：

- 让已有混乱项目能低成本接入系统

本阶段交付物：

- 历史文档角色归类器
- `SSOT / Snapshot / Archive` 建议器
- 迁移顺序建议器
- 风险冲突摘要

阶段门禁：

- 能输出最低成本迁移顺序
- 能识别高频冲突类型
- 输出结果能落回文档系统，而不是停在抽象建议

商业化门槛：

- 这是适合 add-on 或高客单服务入口的能力

### 6.7 Phase 6 · Vertical Packs

目标：

- 用行业规则和模板提升特定场景的采用效率

本阶段交付物：

- 行业版 scaffold
- 行业版规则包
- 行业版检查器映射
- 行业特定报告输出

阶段门禁：

- 行业包必须建立在通用规则层之上
- 行业包不能复制一套完全独立产品
- 每个行业包都要有明确适用边界

商业化门槛：

- 作为高客单扩展层存在，而不是替代核心 Team Plan

## 7. 建议的产品包装顺序

建议先形成三层商业包装：

### 7.1 Team Plan

首个主套餐：

- PR 检查
- 自动巡检
- 健康度面板

### 7.2 Governance Add-on

团队治理增强：

- 团队规则包

### 7.3 Migration / Vertical Add-ons

高价值扩展：

- 迁移助手
- 行业模板包

## 8. 第一批任务清单

建议付费层按下面顺序开工：

1. 定义托管结果存储模型
2. 做 PR diff 到规则上下文的映射
3. 实现 PR 评论与阻断输出
4. 做定时巡检执行器与快照留存
5. 再做健康度面板
6. 再做团队规则包模型
7. 最后做迁移助手与行业模板包

## 9. 非目标

付费层第一轮不要扩到这些方向：

- 通用知识库平台
- 在线 Markdown 编辑器
- 重型审批流
- 大而全项目管理套件
- 与文档系统无关的工程质量平台

这些会让产品偏离 `docs ops workflow` 的核心定位。

## 10. 风险与控制点

### 10.1 风险：面板先于快照

问题：

- 面板会变成没有时间维度的空壳

控制：

- 必须先完成自动巡检和快照留存

### 10.2 风险：PR 检查自己实现私有规则

问题：

- 与 CLI 结果不一致

控制：

- PR 层只消费共享规则引擎结果，不重写规则判断

### 10.3 风险：团队规则包破坏标准结果结构

问题：

- 无法统一统计和聚合

控制：

- 允许覆盖阈值和组合，不允许破坏结果 schema

### 10.4 风险：过早做迁移助手

问题：

- 会在核心工作流未稳定前消耗大量产品精力

控制：

- 迁移助手必须在 PR 检查、巡检、面板之后

## 11. 与免费层的接口

付费层必须直接复用免费层留下的基础接口：

- 规则 ID
- 规则结果对象
- severity 模型
- context 模型
- Markdown / JSON 输出语义

换句话说：

- 免费层定义“怎么判断”
- 付费层定义“怎么持续执行、展示和治理”

## 12. 上线判定

可以把付费层拆成三次对外上线：

### Launch 1

- PR 检查

目标：

- 验证最强付费触点是否成立

### Launch 2

- 自动巡检
- 健康度面板

目标：

- 验证持续治理价值

### Launch 3

- 团队规则包
- 迁移助手
- 行业模板包

目标：

- 验证高客单扩展层

## 13. 结论

付费层现在可以提前规划，但不应脱离免费层和共享规则层单独设计。

最合理的推进顺序是：

1. 免费层完成
2. 共享规则结果稳定
3. `PR 检查`
4. `自动巡检`
5. `健康度面板`
6. `团队规则包`
7. `迁移助手`
8. `行业模板包`

这份文档的作用，就是把付费层从“能力列表”变成“可执行的产品计划”。
