# Open Core 产品边界

Last Updated: 2026-03-12
Status: Active

## 1. 目标

这份文档定义 VibeCoding Documentation OS 的产品边界：

- 哪些能力属于开源核心
- 哪些能力属于付费工作流
- 为什么这样切分
- 后续新增能力如何归类

核心原则不是“把基础能力阉割后收费”，而是：

- 免费层负责让用户可以真正开始使用
- 付费层负责让团队可以长期维持质量和协作效率

## 2. 总体定位

产品分三层：

1. `Open Templates Layer`
   - 模板
   - scaffold
   - 方法论文档
2. `Open CLI Layer`
   - 本地初始化
   - 本地生成功能包
   - 本地巡检与报告
   - 共享规则引擎
3. `Paid Workflow Layer`
   - PR 检查
   - 健康度面板
   - 自动巡检
   - 团队规则包
   - 迁移助手
   - 行业模板包

## 3. 切分原则

### 3.1 开源层必须完整可用

开源层必须能让一个普通开发者或小团队：

- 从 0 初始化文档系统
- 为新功能补齐最小文档骨架
- 在本地做基础巡检
- 基于 Markdown 和 Git 独立运行

如果没有付费产品就无法使用这套系统，开源层就没有传播力。

### 3.2 付费层只卖持续工作流，不卖基础写作权

付费层不应该把“新建模板、复制骨架、填写文档”这种基础权利锁住。

付费层要卖的是：

- 团队协作中的自动约束
- 跨 PR / 跨迭代 / 跨仓库的持续检测
- 更强的规则系统和行业资产
- 更低的人力迁移成本

### 3.3 文档格式必须开放

无论免费还是付费，都坚持：

- Markdown 优先
- Git 优先
- 文件系统优先
- 不把用户的文档锁进私有格式

这样付费层才是增强器，不是绑架器。

## 4. 开源核心包含什么

开源核心明确包括：

### 4.1 内容资产

- 方法论文档
- 模板目录
- scaffold 目录
- 基础提示词

### 4.2 本地 CLI 能力

- `vibedocs init`
- `vibedocs feature create`
- `vibedocs audit`
- `vibedocs glossary check`

### 4.3 共享规则引擎

- 通用规则定义
- 标准结果格式
- 本地规则执行器
- CLI 与付费工作流共用的判断核心

### 4.4 本地规则能力

- SSOT 基础检查
- 文档缺失检查
- 文件命名和目录检查
- 术语冲突基础检查
- 文档状态字段完整性检查

### 4.5 本地输出

- Markdown 报告
- CLI 终端摘要
- 对应文件的待更新建议

## 5. 付费工作流包含什么

付费层明确包括：

### 5.1 PR 检查

- 基于 diff 判断哪些文档应该更新
- 在 PR 中直接给出阻断或建议
- 识别“代码已变，Spec 未变”一类问题

### 5.2 文档健康度面板

- 以仓库、团队、周期维度展示健康度
- 显示缺失文档、冲突 SSOT、长期未更新文档
- 追踪趋势，而不是单次扫描结果

### 5.3 自动巡检

- 定时运行健康检查
- 自动生成周报或告警
- 对关键漂移问题建立历史记录

### 5.4 团队规则包

- 自定义文档门禁
- 自定义目录与命名约束
- 角色与流程特定规则

### 5.5 迁移助手

- 对既有项目做角色归类
- 给出最低成本迁移顺序
- 辅助标记 `SSOT / Snapshot / Archive`

### 5.6 行业模板包

- 面向特定行业提供更强约束模板
- 如 SaaS、内容产品、AI Agent、移动应用等

## 6. 硬边界

下面这些边界必须长期稳定：

| 能力 | 开源 | 付费 | 原因 |
|---|---|---|---|
| 模板与 scaffold | Yes | No | 属于分发和采用入口 |
| 共享规则引擎与标准结果格式 | Yes | No | 属于统一判断逻辑的基础设施 |
| 本地初始化 | Yes | No | 属于基本可用性 |
| 本地功能包生成 | Yes | No | 属于日常开发基础动作 |
| 本地基础巡检 | Yes | No | 属于建立信任的最低门槛 |
| PR 内自动评论 / 阻断 | No | Yes | 属于团队协作自动化 |
| 历史趋势与健康面板 | No | Yes | 属于持续运营能力 |
| 定时自动巡检 | No | Yes | 属于持续服务能力 |
| 团队级规则中心 | No | Yes | 属于组织能力增强 |
| 复杂项目迁移助手 | No | Yes | 属于高价值迁移服务 |
| 行业专用规则包 | Mixed | Mixed | 保留基础版，深度版付费 |

## 7. 何时允许 Mixed 模式

少数能力允许基础版开源、高级版付费：

### 7.1 规则系统

- 开源：内置通用规则和共享执行引擎
- 付费：团队规则包、规则组合、规则治理

### 7.2 行业模板

- 开源：少量通用示例
- 付费：完整行业包、规则和检查器联动

### 7.3 巡检

- 开源：本地手动运行
- 付费：自动运行、历史保存、团队通知

## 8. 新能力归类判断法

以后新增一个能力时，按下面顺序判断：

1. 如果没有它，单个开发者还能不能完整用起来
2. 如果它的主要价值来自自动化协作、持续托管、团队规则，就优先归入付费层
3. 如果它只是本地创作或本地检查增强，就优先归入开源层
4. 如果它既有基础版又有团队增强版，就采用 `Mixed`

## 9. 反模式

以下做法会破坏 open core 路线：

- 把基础模板生成能力锁进付费层
- 把本地 audit 故意做得不可用，只逼用户上云
- 让付费产品要求私有文档格式
- 先卖面板，再不解决初始化和落地
- 把咨询服务和产品能力混为一谈

## 10. 当前结论

这条产品路线应坚持一句话：

`Open core solves startup. Paid workflows solve long-term discipline.`

免费层解决“怎么开始”，付费层解决“怎么长期不烂”。
