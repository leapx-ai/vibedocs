# 付费工作流能力包

Last Updated: 2026-03-12
Status: Active

## 1. 目标

定义付费层到底卖什么，不卖什么，以及各能力包之间的关系。

付费层不是“更多模板”，而是围绕团队协作、持续约束和迁移效率的工作流产品。

所有付费能力都应建立在共享规则引擎之上，而不是各自维护私有判断逻辑。

## 2. 付费层总原则

### 2.1 卖持续性，不卖一次性生成

付费层优先承载：

- 自动执行
- 团队规则
- 历史趋势
- 多人协作
- 迁移成本下降

### 2.2 卖结果约束，不卖阅读材料

用户付费不是为了再多看几篇文档，而是为了：

- 少漏改
- 少返工
- 少口径漂移
- 少迁移成本

### 2.3 每个能力包都要有独立触发场景

如果一个能力没有明确触发场景，它就不应单独成为产品能力。

## 3. 能力包总览

| 能力包 | 核心对象 | 核心触发点 | 核心输出 |
|---|---|---|---|
| PR 检查 | 开发团队 | 提交 PR 时 | 评论、阻断、修复建议 |
| 文档健康度面板 | Team Lead / PM | 周期性查看 | 趋势、风险、缺口 |
| 自动巡检 | 团队 / 仓库 | 定时任务 | 周报、告警、问题清单 |
| 团队规则包 | 团队管理员 | 建规则时 | 规则集、门禁策略 |
| 迁移助手 | 旧项目负责人 | 上线前迁移 | 迁移建议、分类、标记 |
| 行业模板包 | 特定行业团队 | 初始化或扩展时 | 行业文档包与规则 |

## 4. 能力包一：PR 检查

### 4.1 用户问题

代码改了，但对应文档没改，团队往往只能在 merge 后才发现。

### 4.2 触发场景

- 创建或更新 PR
- 大范围 diff
- 关键目录变化

### 4.3 输入

- 共享规则引擎结果
- PR diff
- 仓库文档结构
- SSOT map
- 团队规则包

### 4.4 输出

- 缺失文档更新提示
- 风险评论
- 可选阻断结论
- 建议更新的具体文档列表

### 4.5 为什么适合收费

它的价值来自：

- 持续运行
- 平台集成
- 团队级门禁

这不是本地 CLI 能替代的。

## 5. 能力包二：文档健康度面板

### 5.1 用户问题

团队无法判断文档系统整体是在变好还是变坏，只能看零散扫描结果。

### 5.2 触发场景

- 周会前查看
- 发布前查看
- 团队治理复盘

### 5.3 输入

- 定时巡检快照
- 每次 audit 结果
- PR 检查历史
- 文档更新时间与状态字段

### 5.4 输出

- 健康度评分
- 风险趋势
- SSOT 冲突数量
- 长期未更新文档清单

### 5.5 为什么适合收费

它依赖历史存储、趋势分析和多次运行结果聚合。

## 6. 能力包三：自动巡检

### 6.1 用户问题

即使知道要巡检，团队也常常不会主动运行 audit。

### 6.2 触发场景

- 每日或每周定时
- 发布前定时
- 仓库关键变更后

### 6.3 输入

- 共享规则引擎
- 仓库当前状态
- 团队规则包
- 历史健康记录

### 6.4 输出

- 周报
- 告警
- 待处理问题列表

### 6.5 为什么适合收费

它的本质是托管式持续服务，而不是一次性本地工具。

## 7. 能力包四：团队规则包

### 7.1 用户问题

不同团队的门禁不同，通用规则不够用，但每个团队又不想自己写一套系统。

### 7.2 触发场景

- 团队想定义强约束
- 团队分角色协作
- 行业合规要求更高

### 7.3 输入

- 团队文档规范
- 角色分工
- 发布和评审流程

### 7.4 输出

- 可复用规则集
- 规则优先级
- 对 PR 检查和自动巡检的约束

### 7.5 为什么适合收费

团队规则一旦成立，会直接影响团队协作效率，是明确的组织价值。

## 8. 能力包五：迁移助手

### 8.1 用户问题

已有项目最大的问题不是“没有模板”，而是历史文档太乱，不知道如何最低成本迁移。

### 8.2 触发场景

- 旧项目接入系统
- 文档已严重漂移
- 团队准备建立正式治理

### 8.3 输入

- 仓库现有文档目录
- 代码现状
- 现有命名和状态冲突

### 8.4 输出

- 文档角色归类
- `SSOT / Snapshot / Archive` 建议
- 最低成本迁移顺序
- 高风险冲突项

### 8.5 为什么适合收费

它节省的是高成本的人力分析时间，且更接近高客单服务入口。

## 9. 能力包六：行业模板包

### 9.1 用户问题

通用模板可以启动，但某些行业需要更强的规则和字段约束。

### 9.2 触发场景

- 新行业项目初始化
- 现有项目进入特定合规或运营场景

### 9.3 输入

- 行业类型
- 业务模式
- 常见流程与指标

### 9.4 输出

- 行业版 scaffold
- 行业专用模板
- 配套规则和巡检项

### 9.5 为什么适合收费

行业 know-how 不是通用基础设施，而是高价值知识资产。

## 10. 推荐打包方式

### 10.1 Team Plan

适合日常团队使用：

- PR 检查
- 自动巡检
- 文档健康度面板
- 基础团队规则包

### 10.2 Migration Add-on

适合旧项目接入：

- 迁移助手
- 一次性迁移诊断报告

### 10.3 Vertical Pack Add-on

适合行业团队：

- 行业模板包
- 行业规则包

## 11. 依赖顺序

具体执行顺序、阶段门禁和上线分批，见 `../plans/PAID-LAYER-IMPLEMENTATION-PLAN.md`。

付费层不应同时启动全部能力，建议顺序如下：

1. `共享规则引擎`
2. `PR 检查`
3. `自动巡检`
4. `文档健康度面板`
5. `团队规则包`
6. `迁移助手`
7. `行业模板包`

原因：

- 共享规则引擎决定各产品是否输出一致结果
- PR 检查是最直接、最刚需的付费触点
- 自动巡检先提供持续数据源，再喂给面板
- 团队规则包会放大前两者价值
- 迁移助手和行业模板包更适合作为高客单扩展层

## 12. 不应该收费的东西

以下内容不应作为付费核心：

- 基础模板复制
- scaffold 初始化
- 本地手动 audit
- 本地 feature package 创建
- 基础方法论文档阅读权

如果这些都收费，整个产品的采用成本会过高。

## 13. 结论

付费层的逻辑应该保持稳定：

- `PR 检查` 解决 merge 前约束
- `自动巡检 + 健康面板` 解决持续治理
- `团队规则包` 解决组织差异
- `迁移助手 + 行业模板包` 解决高价值扩展

这样免费层和付费层之间才会形成清晰、可持续的产品分工。
